# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Sobre o projeto

Sistema de gestão de pontos de doação/coleta com rastreabilidade por beneficiário e **controle de equidade**:
todos os pontos de coleta de um município compartilham o histórico de retiradas, então um beneficiário não
pode exceder seu limite por ciclo somando retiradas de *todos* os pontos. .NET 9 / C# 13, Clean
Architecture + DDD + CQRS, EF Core 9 + PostgreSQL 16.

## Estilo de código (front e back)

Vale para todo o monorepo (`backend/` e `frontend/`): o código se autoexplica, então **não usamos comentários
inline**. A clareza vem dos nomes e do tamanho das funções, não de comentários.

- **Sem comentários `//` nem `/* */`** no meio do código. Se algo precisa de comentário para ser entendido,
  refatore: extraia um método/função com nome descritivo ou renomeie a variável.
- **Nomes que descrevem a intenção**: métodos, funções, variáveis, constantes e tipos devem dizer *o que*
  fazem/representam. Prefira `beneficiaryWithdrawalsInCurrentCycle` a `count`; extraia constantes nomeadas no lugar
  de literais "mágicos".
- **Métodos e funções curtos**, com responsabilidade única — fáceis de ler de cima a baixo sem explicação.
- **A única documentação permitida** é a de API: XML docs `///` no C# (back) e JSDoc/TSDoc quando documentar
  contrato público no front. Nada de comentário explicando *como* o código funciona por dentro.
- **Exceção**: arquivos auto-gerados (ex.: `Persistence/Migrations/` com `// <auto-generated />`) ficam como estão.

## Práticas de desenvolvimento

- **TDD em regra de negócio**: para um comportamento novo ou alterado num agregado ou Handler
  crítico, o teste que falha vem primeiro (`DoacaoApp.Domain.Tests` / `DoacaoApp.Application.Tests`),
  a implementação depois. Não é "escrever teste depois" — ver "Cobertura obrigatória" no README.md.
- **Sem primitive obsession**: campo com validação, formato ou igualdade própria (documento,
  e-mail, período, faixa de valores...) é Value Object (`Create` retornando `ErrorOr`), nunca um
  `string`/`int` cru trafegando entre camadas — é o mesmo padrão de `Cpf`/`Email`/`PhoneNumber`.
- **C# idiomático e performático** (.NET 9 / C# 13): prefira a API mais nova quando for claramente
  melhor — collection expressions (`[]`), primary constructors, pattern matching, `is null`/
  `is not null`, `FrozenDictionary`/`FrozenSet` para lookup estático, `Span<T>`/`ReadOnlySpan<T>`
  em parsing sensível a alocação. Não troque API antiga por nova só por novidade — só quando for
  mais legível ou mensuravelmente melhor.

## Ambiente: SDK .NET só para o editor

O host tem apenas o SDK .NET 10 (o `backend/global.json` usa `rollForward: latestMajor` para o VS Code
funcionar com ele). Compilação, testes e geração de migration rodam dentro de containers do SDK .NET 9.
Monte um volume NuGet persistente (`doacao-nuget`) para não rebaixar pacotes a cada execução e mande
`bin/`/`obj/` do container para o volume `doacao-artifacts` com `--artifacts-path /artifacts`: assim o
container nunca escreve em `backend/` (nem deixa arquivos de root) e o `obj/` do host, usado pelo editor,
continua válido. O cache do container é efêmero, então **nunca use `--no-restore` em um container novo**.

### Comandos (via Docker)

```bash
# Build de toda a solution (src + testes)
docker run --rm -v "$PWD/backend":/src -v doacao-nuget:/root/.nuget -v doacao-artifacts:/artifacts -w /src \
  mcr.microsoft.com/dotnet/sdk:9.0 dotnet build DoacaoApp.sln -c Release --artifacts-path /artifacts

# Testes unitários (rápidos, sem Docker-in-Docker) — um projeto por vez
docker run --rm -v "$PWD/backend":/src -v doacao-nuget:/root/.nuget -v doacao-artifacts:/artifacts -w /src \
  mcr.microsoft.com/dotnet/sdk:9.0 dotnet test tests/DoacaoApp.Domain.Tests -c Release --artifacts-path /artifacts

# Um único teste / filtro
docker run --rm -v "$PWD/backend":/src -v doacao-nuget:/root/.nuget -v doacao-artifacts:/artifacts -w /src \
  mcr.microsoft.com/dotnet/sdk:9.0 \
  dotnet test tests/DoacaoApp.Domain.Tests -c Release --artifacts-path /artifacts --filter "FullyQualifiedName~CpfTests"

# Nova migration (constrói o modelo — falha aqui se o mapeamento EF estiver errado)
docker run --rm -v "$PWD/backend":/src -v doacao-nuget:/root/.nuget -w /src mcr.microsoft.com/dotnet/sdk:9.0 \
  bash -c "dotnet tool install -g dotnet-ef --version 9.0.0 >/dev/null; export PATH=\$PATH:/root/.dotnet/tools; \
  dotnet ef migrations add <Nome> -p src/DoacaoApp.Infrastructure -s src/DoacaoApp.Api -o Persistence/Migrations"
```

Os testes de integração (`DoacaoApp.IntegrationTests`) usam **Testcontainers** e exigem acesso ao socket
do Docker; rodam melhor no host com SDK ou em CI, não dentro de um container SDK simples.

### Subir a aplicação

```bash
cp .env.example .env
docker compose up --build        # postgres + minio (healthcheck) -> api -> pgadmin + frontend
```
Só o `dotnet ef migrations add` ainda grava em `backend/` (os arquivos de `Persistence/Migrations` saem como `root`); faça
`docker run --rm -v "$PWD/backend":/src alpine chown -R "$(stat -c '%u:%g' backend/DoacaoApp.sln)" /src` se precisar editá-los.

## Arquitetura

Dependências apontam para dentro: **API → Infrastructure → Application → Domain**. O Domain não referencia
framework algum (só `ErrorOr` e `MediatR.Contracts`). Cada camada tem um `DependencyInjection` /
`ServiceCollectionExtensions` que é seu composition root.

- **Result Pattern**: fluxo de negócio nunca lança exception — retorna `ErrorOr<T>`. Erros de domínio ficam
  centralizados em `Domain/Errors/DomainErrors.cs` (e `Application/Authentication/AuthErrors.cs`). A API
  mapeia `ErrorType` → status HTTP em `Api/Common/HttpErrorMapping.cs` (controllers via `ApiController.Respond`,
  minimal APIs via `MinimalApiResults.Match`).
- **CQRS (MediatR)**: cada caso de uso é um `IRequest<ErrorOr<T>>` + Validator + Handler, geralmente no mesmo
  arquivo (vertical slice). O `ValidationBehavior` roda os `FluentValidation` validators antes do handler;
  ele usa `(dynamic)errors` para converter `List<Error>` no `TResponse` genérico — por isso exige
  `where TResponse : IErrorOr`.
- **Domain Events**: entidades acumulam eventos (`Entity.RaiseDomainEvent`); o
  `DomainEventsDispatchInterceptor` os publica via MediatR **após** o commit do `SaveChanges`. `IDomainEvent`
  herda de `INotification`, então os handlers ficam na Application como `INotificationHandler<T>`.

### A regra de equidade (a parte mais importante)

`CollectionPoint.RegisterWithdrawal(beneficiary, beneficiaryWithdrawalsInCurrentCycle, ...)` decide com
base na contagem **recebida por parâmetro** — o agregado não consulta o banco. Quem calcula é o
`RegisterWithdrawalHandler`: ele pega a janela do ciclo (`CollectionPoint.WithdrawalRule.GetCurrentPeriod(instante)`) e chama
`ICollectionPointRepository.CountBeneficiaryWithdrawalsAsync(beneficiaryId, início, fim)`, que varre a tabela
`withdrawals` inteira (todos os pontos). Esse desenho mantém a regra testável sem banco e respeita as
fronteiras de agregado (Withdrawal referencia Beneficiary por Id, não por navegação).

O `Beneficiary` é único por CPF no município, mas pode ser atendido por vários pontos: `PointLinks`
(`BeneficiaryPointLink`) guarda os pontos vinculados, `RegisteredByPointId` só registra quem fez o cadastro
original, e a visibilidade/edição de um gestor vale para quem está vinculado ao seu ponto
(`Beneficiary.IsLinkedTo`, `LinkBeneficiaryToPointCommand`). Toda retirada (uma visita) tem uma ou mais categorias (`Withdrawal.Categories`, coluna `text[]`); só as **cestas básicas** (`ItemCategory.Food`,
`ItemCategoryExtensions.CountsTowardsWithdrawalLimit`) estão sujeitas ao limite por ciclo — as demais
(roupas, calçados…) são livres, mas ficam no histórico do beneficiário. Só é possível retirar categorias
com quantidade positiva no `CollectionPoint.Stock` do próprio ponto no momento do registro — é o mesmo
agregado que decide isso, sem I/O extra (`RegisterWithdrawal` verifica antes do limite de ciclo). Não
existe o conceito de "família": o `Beneficiary` é o Aggregate Root e não guarda limite algum. A regra
de retirada (`WithdrawalCycle`: tipo do ciclo + máximo por família; padrão: 3 por ano) é do **ponto**
(`CollectionPoint.WithdrawalRule`, configurada na aba "Metas e avisos" do estoque): o histórico é somado entre
todos os pontos, mas o limite aplicado é o do ponto onde a retirada acontece. Vínculos de parentesco
(`BeneficiaryKinship`) são só informativos — espelhados no outro beneficiário com o tipo inverso.

### Módulos além do core (Reviews, Storage, Stock)

- **`Review`** (Aggregate Root próprio, em `Domain/Reviews`) — avaliação pública de um ponto
  (nota 1–5 + comentário), referencia `CollectionPointId` por Id. Moderação é lógica (`Hide`/`Restore`),
  nunca `DELETE`.
- **`StoredFile`** (Aggregate Root próprio, em `Domain/Storage`) — metadado de arquivo em object
  storage S3-compatível (MinIO local / Amazon S3 em prod, `AWSSDK.S3`). Vínculo com o dono
  (`OwnerType`/`OwnerId`) é **propositalmente fraco, sem FK** — não assuma navegação EF nem cascade.
  Exclusão é soft-delete (`MarkDeleted`): a linha permanece para auditoria, só o objeto some do bucket.
- **Estoque** — `CollectionPoint.Stock` é um dicionário `ItemCategory → quantidade`, substituído por
  inteiro via `ReplaceStock` (não incrementado/decrementado por item).
  `CollectionPoint.StockSettings` guarda, por categoria, meta, aviso de estoque baixo e se é acompanhada
  (`ReplaceStockSettings`, coluna JSON `stock_settings`). Só as consultas de gestão devolvem as configurações;
  a lista pública não as expõe.

## Convenções de mapeamento EF (onde as coisas dão errado)

- **IDs fortemente tipados** (`BeneficiaryId`, `CollectionPointId`, etc. — `readonly record struct`): convertidos
  globalmente em `AppDbContext.ConfigureConventions` via os `ValueConverter`s de
  `Persistence/Converters/StronglyTypedIdConverters.cs`. Chaves usam `ValueGeneratedNever()` (o domínio gera o Guid).
- **Value Objects multi-campo** (`Address`, `ContactInfo`, `WithdrawalCycle`): mapeados como `OwnsOne`
  (colunas inline). EF materializa pelo construtor privado via reflection.
- **Value Objects de valor único** (`Cpf`, `Email`, `PhoneNumber`): `HasConversion` para string usando
  `X.FromTrusted(...)` (método `internal`). Isso depende do `InternalsVisibleTo("DoacaoApp.Infrastructure")`
  declarado em `Domain/Common/AssemblyMarker.cs`. As factories públicas `Create` validam e retornam `ErrorOr`.
- Coleções dos agregados (`Withdrawals`, `Beneficiaries`) usam campo privado de backing + `PropertyAccessMode.Field`.
- Datas: tudo em UTC (Npgsql + `timestamptz`). Passe instantes via `IDateTimeProvider`, não `DateTime.UtcNow` direto.

## Identidade e autenticação

- **BCrypt** substitui o hasher padrão do Identity. `BCryptPasswordHasher` é registrado **antes** de
  `AddIdentityCore` em `Infrastructure/DependencyInjection.cs`, porque o Identity usa `TryAdd` e o nosso
  precisa prevalecer. Não readicionar `AddDefaultTokenProviders` (depende do pacote `Microsoft.AspNetCore.Identity`,
  que não está referenciado e não é necessário).
- Os **stores/hashing/geração de token** ficam na Infrastructure (`IdentityService`, `JwtTokenGenerator`);
  o **wiring do JWT Bearer + policies** fica na API (`ServiceCollectionExtensions.AddJwtAuthentication`),
  pois usa o shared framework. Roles: `Admin`, `PointManager`, `Viewer` (`Application/Authentication/Roles.cs`).
- Refresh tokens são persistidos e rotacionados (`IdentityService.RefreshAsync` revoga e emite novo par).

## Pacotes e configuração

- **Central Package Management**: todas as versões vivem em `Directory.Packages.props`; os `.csproj` só fazem
  `<PackageReference Include="..." />` sem `Version`. `Directory.Build.props` fixa `net9.0`/C# 13/nullable.
- Config por ambiente: `appsettings.json` + variáveis com `__` (ex.: `Jwt__Secret`, `ConnectionStrings__Database`)
  vindas do `.env` no compose. `RunMigrationsOnStartup` e `SeedData:Enabled` controlam migrate+seed no boot (dev).
- Docs da API: Scalar em `/scalar/v1`, OpenAPI em `/openapi/v1.json`.
